# 原生缩放验收(真人按键版)2026-11-14

## 为什么重做

前面的两轮都没能触发"真缩放":`SendKeys` 和 CDP `Input.dispatchKeyEvent` 都没让 DPR 变化(见 `../RESULTS.md`)。
这一次由桌宠用**真实键鼠输入**(Windows SendInput 级别)在真窗口上按 Ctrl+= / Ctrl+- / Ctrl+0,一次成功。

## 环境

- 机器:华硕 TUF Gaming F16,屏幕 2560×1600,系统缩放 150% —— 即**物理高分屏**,不是模拟。
- 浏览器:Chrome 157(独立临时 profile,`--remote-debugging-port=19456`,窗口 1280×900)。
- 被测页面:本目录 `fixture.html`,由 `127.0.0.1:8792` 提供(两层卡片 + 两个不同尺寸的目标元素 `#target` 320×120、`#target2` 180×64)。
- 采样:`native-zoom.mjs` 每 400ms 通过 CDP 读 `devicePixelRatio` / `visualViewport.scale` / `innerWidth` / 两个元素的 `getBoundingClientRect()`,变化时自动截页面图。原始读数 `readings.jsonl`,截图 `shots/`。

## 结论

- **通过**:真人按键确实驱动了浏览器原生缩放。DPR 严格等于 `1.5 × 缩放比`(1.5→1.65→1.875→1.35→1.2),`innerWidth` 按缩放反比变化(1266→1151→1013→1407→1582),`visualViewport.scale` 始终 1(缩放走的是浏览器 zoom,不是 pinch-zoom)。
- **通过**:缩放只改"CSS 视口有多大",**不改布局 CSS 坐标** —— 目标元素 x 恒 40、宽恒 320(最大偏差 0.01 CSS px)。所以跑在 CSS px 上的覆盖层、命中判定、锚点重定位天然跟得住缩放。
- **由此推出的风险面**(代码要照这个查):凡是碰设备像素的地方必须乘 DPR —— `captureVisibleTab` 截图尺寸、截图里算出的批注坐标、canvas 的 backing store 尺寸;只用 CSS px 的地方不用改。
- **未覆盖**:本次没有加载扩展做"真按键 + 新建批注 + 发布 pin"的矩阵。那组矩阵在 `docs/zoom-repro-2026-11-13.md` 里用 `chrome.tabs.setZoom`(真浏览器缩放)验过,偏差 -0.5 CSS px;本次只补了"真人按键这一层能真的动"以及"CSS 几何稳定"的前提。
